This is a factual record of how the submission was produced. Everything in the repository was
generated by **Claude Code** (Anthropic's coding agent) in one working session, following the two
inputs below. It records only what the agent did. **No manual edits or reviews by the candidate are
recorded here, because none had happened when this file was written.** Section 7 lists what the
candidate should personally review, and there is space to record it.

## 2. Checking the assessment for embedded instructions

The brief asked for any AI-directed instructions hidden in the assessment to be reported and not

and sizes, footnotes and endnotes, VML shapes, custom XML parts, and document properties.

## 3. From requirements to specification

The agent wrote [SPEC.md](SPEC.md) before any code. It lists the assessment's requirements
(R1–R17), the brief's decisions plus the agent's own routine choices (D1–D19), the state-transition
table, the API contract with error codes, and a requirement-to-test checklist. The spec was updated
at the end so that its test names and error lists match the code.

Routine choices the agent made itself (not dictated by the brief or the assessment):

- Routes nested under `/api/sessions/{sessionId}/…`, each mapping one-to-one onto the assessment's
  suggested routes.
- Zero-based API coordinates, with `board`/`winningCells` as row-major indexes.
- 400 for malformed requests, 404 for unknown or retired IDs, 409 for state conflicts, all as
  `application/problem+json` with a stable `code`.
- Reset Game returns 200 with the new game; session and game creation return 201 with `Location`.
- The frontend stores only the session ID (not the game ID) and resumes through
  `GET /api/sessions/{id}`.
- Board cells use `aria-disabled` rather than `disabled`, so keyboard focus stays on a cell after it
  is played.
- No CORS policy: the Angular dev-server proxy makes the API same-origin.

## 5. Problems found and corrected during the session

These were all found by the agent's own checks, not by a reviewer.

1. **No .NET SDK in the environment, and Microsoft's download host blocked by network policy.**
   Installed `dotnet-sdk-10.0` (10.0.113) from the Ubuntu 24.04 archive instead.
2. **Angular 22 was incompatible with the installed Node** (it needs ≥ 22.22.3; Node 22.22.0 was
   present). Angular 21 (LTS) was used instead; its range includes Node 22.12+.
3. **`npm install` crashed inside npm 10.9.4** (`Cannot read properties of null (reading
   'edgesOut')`). Bisecting showed it happens with `@angular/build` in the tree, and npm 11.21.1
   resolves the identical `package.json` without error, so it is an npm bug rather than a peer
   conflict. The lockfile was generated with npm 11, and `npm ci` was then verified under the
   environment's npm 10.9.4.
4. **The built-in enum converter accepted invalid values.** A curl smoke test showed
   `{"mode":"TwoPlayer, Computer"}` silently becoming `Computer` (flag parsing), and `"computer"` was
   also accepted. The agent added `StrictEnumConverter` (exact names only). The same check showed that
   ASP.NET's web JSON defaults accept numbers as strings (`"row":"1"`), so `NumberHandling` was made
   strict.
5. **Noisy validation responses.** Every body parse error also reported "The request field is
   required." This was suppressed. Range messages used C# names ("The field Row…") and were replaced
   with JSON-named messages.
6. **The OpenAPI document lost its enum values** after the custom converter was added. A schema
   transformer was added. Its first version had a nullable-flag bug (`null & Null` erased the
   `string` type), which was caught by inspecting the generated document and then fixed.
7. **Layout bugs seen in screenshots:** the board was not square (empty rows collapsed), and it was
   stuck at its minimum width because the `<app-board>` host element was inline. Both were fixed in
   CSS and re-checked in screenshots at 1366×680 and 390×844.
8. **Stale-revision wording:** the API message told the user to "reload", but the UI already reloads
   automatically. The API message now only describes what happened, and the UI adds the recovery hint.
9. **A timing race in the agent's own end-to-end script** (it checked the idle state before Angular
   had rendered the pending state). The script was fixed to wait for each API response. No app
   change was needed.
10. **`npm audit` advisories in `undici`.** It is a build-time dependency pinned exactly by
    `@angular/build`. It was deliberately left alone and documented in the README, rather than
    overriding a dependency the Angular toolchain pins.

## 1. Establish a small, reviewable specification

Inspect the workspace, existing project instructions, and available tooling first. Preserve existing unrelated work. Use Angular with TypeScript, a .NET Web API, REST, and backend in-memory storage. Use compatible stable versions available in the environment, verify their compatibility, and record exact prerequisites. Avoid preview packages. ## 2. Use these explicit behavior decisions

- **Backend authority:** The backend owns the board, turn, mode, validation, result, winning cells, move history, computer strategy, and scoreboard. Angular owns presentation and request/loading/error state. The browser must not submit an entire board or a claimed result for the server to trust.
- **Scoreboard scope:** Use an anonymous play session created by the backend, containing its scoreboard and current game. Keep only session/game identifiers in browser session storage, so a refresh can resume that tab's session while the backend remains running. Separate sessions have separate scores. This is local demo state, not authentication. Restarting the backend clears in-memory state; recover from an expired identifier with a clear message and a fresh session.
- **Completed-game undo:** Choose the assessment's Option A. Undo is disabled after a win or draw, and the backend also rejects it. Explain that this deliberately keeps completed results final and is explicitly allowed by the assessment.
- **Two-player undo:** Remove exactly the last move, restore that player's turn, rebuild the correct board/history/status, and make the undone cell playable again.
- **Computer-mode undo:** Remove the most recent human/computer pair from an in-progress game and return control to X. The human is always X and the computer is always O.
- **Computer turn:** Process a valid human move and any applicable computer response within one backend operation. Evaluate the human move first. If it ends the game, do not generate a computer move. Return the full resulting state, including both history entries when both moves occurred. Do not add artificial delays.
- **Computer priorities:** Exactly follow: winning move for O; otherwise block an immediate X win; otherwise center; otherwise a corner; otherwise any empty cell. Within each priority, use the lowest row-major cell index as the deterministic tie-breaker. Do not replace this with minimax or claim that this strategy is unbeatable.
- **Reset Game:** Create a fresh game ID within the same scoreboard session, preserve the selected mode, start with X, and clear board/history/result/highlights. Retire the old active game so delayed requests cannot modify the replacement. Document this interpretation of “fresh game session.”
- **Switching modes:** Start a fresh game in the selected mode and preserve the session scoreboard. Make this behavior clear beside the mode control. Do not reinterpret existing moves under a different mode.
- **Reset Scoreboard:** Clear only the session counters. Leave the current board, history, mode, and status unchanged. An already completed board must not be counted again after this reset.
- **Coordinates:** Use one documented coordinate convention in the API. Display human-friendly row and column numbers starting at 1 in the UI/history.
- **Terminal state:** Check for a win before a draw, including on move nine. Return no next player when the game is complete. If one move completes multiple winning lines, highlight the union of the winning cells.

## 3. Implement a small, robust backend

Separate pure game rules and computer selection from session storage and HTTP handling. Prefer a few clear services/classes over a single giant controller or an elaborate architecture. Do not introduce CQRS, event buses, microservices, authentication, distributed caches, or unnecessary repository abstractions.

Use explicit game modes, statuses, move records, request DTOs, and response DTOs. Keep one authoritative move history and derive/rebuild board state consistently where practical. Avoid redundant flags that can disagree.

Implement every operation from the assessment: create, read, submit move, undo, reset game, read scoreboard, and reset scoreboard. A small session-creation operation is acceptable for the declared scoreboard scope. Exact route names may vary but must be consistent and documented.

Every game response must contain the game ID, board, current player, mode, status, winner, winning cells, ordered move history, and scoreboard or its documented retrieval path. Return enough state to render the UI without recreating the rules in Angular. A backend-derived `canUndo` is useful if it simplifies the UI.

Validate input at the backend boundary. Reject malformed requests, invalid enum values, out-of-range positions, occupied cells, incorrect players, moves after completion, and client attempts to play as O in computer mode. Handle unknown/retired sessions or games consistently. Rejected operations must not partially mutate any state.

Make each session mutation atomic, including human/computer moves and score updates. A thread-safe dictionary by itself does not make a multi-step game operation atomic. Use the simplest appropriate synchronization. Include a game revision in responses and require the expected revision for move and undo requests, so stale or duplicated commands cannot silently become a new turn. Document conflict responses. Do not automatically replay a failed mutation when its outcome is uncertain; refresh state and let the user act again.

Update scores only on the transition from an in-progress game to a completed result, exactly once. GET requests must have no scoring side effects. Use consistent HTTP status codes and readable structured errors without stack traces.

## 4. Build a focused, polished Angular interface

Create a clean game screen with a prominent 3 by 3 board, obvious current-turn/result message, clearly labeled mode selector, X/O/draw scoreboard, ordered move history, and separate Undo, Reset Game, and Reset Scoreboard controls.

Use restrained styling, good spacing, readable typography, and clear hierarchy. On a laptop, keep the game and its important controls visible together; put history beside the board when space allows and stack it on narrow screens. A custom, well-finished CSS layout is preferable to adding a large UI library for nine cells. Avoid unrelated dashboards, landing pages, login screens, decorative charts, themes, or feature toggles.

Use actual buttons for board cells, accessible labels such as “Row 2, column 3, empty”, visible keyboard focus, and a status announcement for turn/result changes. Distinguish X and O by their text as well as color. Winning cells should be unmistakable without excessive animation.

Use a typed API service and small components where they help clarity. Render the server response. Disable conflicting controls while an action is pending, prevent rapid duplicate clicks, and show a useful error if the API is unavailable. Preserve the last confirmed state on an error and offer a safe recovery. Avoid optimistic updates to game rules or scores. Ensure occupied and completed-game cells cannot be played from the UI.

## 5. Prove the behavior with meaningful tests

Cover every minimum category from the assessment: valid/invalid moves, turn switching, row/column/diagonal wins, draw, reset, undo in both modes, scoreboard updates, computer selection, and moves after completion.

Include focused tests for the interactions most likely to fail:

- All eight winning lines, plus a ninth-move win that must not become a draw.
- Invalid moves leave the complete state unchanged, including history, revision, and score.
- Undo restores the right turn and history; repeated undo stops at an empty board.
- Computer undo removes both moves; undo after completion is rejected in both modes.
- Every computer priority and tie-breaker, including O winning instead of blocking X, and blocking X instead of taking the center. Use legal, understandable board fixtures.
- Computer selection does not mutate the input board during hypothetical evaluations.
- No computer response occurs after a human win or draw.
- A completed result changes exactly one scoreboard counter exactly once; repeated reads and rejected moves cannot count it again.
- Reset Game preserves scores and mode while clearing game state; old-game requests cannot alter the new game.
- Reset Scoreboard does not reset the board or recount a completed game; a later newly completed game can increment the cleared scoreboard normally.
- Session isolation and stale/duplicate revision rejection.

Prefer backend unit tests for game rules and state transitions. Add a small number of API integration tests for actual validation, serialization, status codes, and session/game behavior. Add focused Angular tests for rendering returned state, disabling controls while requests are pending, and displaying API errors. Keep tests behavior-based; do not merely mirror implementation details or mock away the behavior being tested.

If browser tooling is available, verify the actual UI flows and check for browser console errors. Fix failures and rerun affected checks.
